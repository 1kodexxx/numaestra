# Подключение CDN (Yandex CDN перед Object Storage)

CDN ускоряет отдачу треков, демо и обложек и снижает исходящий трафик с бакета.
Приложение готово к переключению **одной env-переменной** — `S3_PUBLIC_BASE_URL`.

## Как это работает в коде

- `S3_PUBLIC_BASE_URL` задаёт базу **публичных** ссылок (только чтение). Все новые
  ссылки строятся как `{S3_PUBLIC_BASE_URL}/{key}`.
- **Загрузка и удаление** объектов по-прежнему идут на `S3_ENDPOINT` (реальный
  S3-API) — CDN не принимает `PUT`/`DELETE`.
- Удаление демо (`DeleteByURL`) понимает **оба** домена — и CDN, и прямой
  S3-origin, — поэтому старые ссылки (созданные до CDN) тоже корректно удаляются.
- Пусто → поведение как раньше: `{S3_ENDPOINT}/{S3_BUCKET}/{key}` (без CDN).

## Шаги

### 1. Настроить CDN в консоли Yandex
- Создать CDN-ресурс, **origin = бакет** Object Storage (`numaestra-tracks`).
- Объекты бакета должны быть **публично читаемыми** (они и так читаются по прямым
  ссылкам — значит уже public-read).
- Привязать домен (напр. `cdn.numaestra.ru`) + TLS-сертификат.

### 2. Установить env и задеплоить
```
S3_PUBLIC_BASE_URL=https://cdn.numaestra.ru          # origin = бакет (virtual-hosted)
# или, если CDN отдаёт path-style:
# S3_PUBLIC_BASE_URL=https://cdn.numaestra.ru/numaestra-tracks
```
Проверить маппинг: ссылка `{S3_PUBLIC_BASE_URL}/tracks/<любой-существующий-key>`
должна отдавать тот же файл, что и прямая S3-ссылка.

С этого момента **новые** треки получают CDN-ссылки; **старые работают как прежде**
(по прямым S3-ссылкам) — ничего не ломается.

### 3. (Опционально) перевести старые ссылки на CDN
Разовая миграция доменов в БД — см. `deploy/cdn-migrate-urls.sql`. До миграции
старые треки тоже доступны, просто мимо CDN.

## ⚠️ Обязательно настроить на стороне CDN

1. **Проброс `Content-Disposition`.** Кнопка «Скачать» работает за счёт заголовка
   `Content-Disposition: attachment`, который ставит S3 при загрузке. CDN **не
   должен вырезать заголовки origin** — иначе скачивание превратится в проигрывание
   во вкладке.

2. **Инвалидация кэша при перегенерации.** Ключи финальных треков
   (`tracks/{id}/{n}.mp3`) и витринного демо (`demos/{id}.mp3`) **детерминированы**:
   при `RegenerateOrder` новый файл пишется в тот же ключ. Закэшированный CDN будет
   отдавать **старое аудио** до истечения TTL. Решения (любое):
   - сбрасывать кэш CDN для путей заказа при перегенерации (Purge API), **или**
   - короткий TTL на `tracks/*` и `demos/*`, **или**
   - принять задержку (перегенерация — редкая ручная операция).
   Полные демо-клипы (`tracks/{id}/demo-<uuid>.mp3`) безопасны — у них в ключе
   случайный UUID, коллизии кэша нет.

## Откат

Убрать `S3_PUBLIC_BASE_URL` (или очистить) и задеплоить — новые ссылки снова станут
прямыми S3. Уже выданные CDN-ссылки продолжат работать, пока CDN-ресурс жив. Если
делали миграцию БД (шаг 3) — прогнать `cdn-migrate-urls.sql` с переставленными
местами `old_base`/`new_base`.
